## 目标

后端具备三项能力，前端 P4.3 接上之后即可使用：
1. 学习者开新对话时，对上一段对话做一次会后提取，产出经历**候选**（不是事实）。
2. 学习者可以通过 HTTP 接口查看、确认、拒绝、遗忘记忆，也可以整体关闭记忆功能。
3. 新对话开头：用规则判断要不要提议"接着练上次的场景"；对话过程中，只把学习者确认过的经历摘要注入 planner。

## 契约（R2：必须逐字照办）

### 存储

```python
# learner_memory.py
def touch(self, session_id, title=None, status=None, pinned=None, bump=True,
          scene_id: Optional[str] = None) -> None: ...   # scene_id 非 None 时写入（截断 80）
def previous_session(self, exclude_session_id: str) -> Optional[dict]:
    """除 exclude 外 updated_at 最大、且至少有 1 条 user 消息的会话：
    {"session_id","scene_id","title","updated_at","memory_scanned_at"}；没有则 None。"""
def mark_memory_scanned(self, session_id: str) -> None: ...  # 写当前时间，不改 updated_at
```

`dialog_run`：如果 `ctx["scene_id"]` 非空，就在每轮写回时调用 `touch(conversation_id, scene_id=..., bump=False)`，失败不阻断。

### 提取器（`extractor.py`）

```python
EXTRACTOR_VERSION = "p42-v1"
MAX_CANDIDATES = 3
def should_extract(user_texts: list[str]) -> bool: ...
def extract_candidates(user_texts: list[str], *, client, native_lang: str = "") -> list[dict]:
    """返回 [{"summary","place"?,"when"?,"tags"?}]，最多 3 条；任何异常都返回 []，不抛出。"""
```

- **只喂 user 消息**：不喂 assistant 回复，取最后 20 条，每条截断 200 字。
- `should_extract`：命中第一人称经历模式才返回 True。模式是"我"加上时间、去向、计划类词，例如 去/去了/在/住/来自/上周/昨天/周末/打算/想去/要去/以前。具体正则由 Codex 定，但必须有正例和反例测试，覆盖「我上周去了长城」=True、「这个怎么说？」=False、「我把这本书不能看完」=False。
- Prompt 要求：只抽学习者**亲口说出**的关于自己的地点、经历、计划，不推断；summary 用简短中文，≤40 字；不抽健康、宗教、政治、性取向、民族、财务、精确住址、电话、证件号，也不抽第三方的全名。
- 用 `client.chat_json_strict(...)`，捕获 `JSONStrictError` 和任何其他异常，一律返回 `[]`。
- 输出要做后置过滤：去掉不是 dict 的项、summary 为空的项、含 `CONTENT_FIELDS["life_event"]` 以外键的项（直接丢弃，不报错）；结果截到 3 条。

### 开场（`opening.py`）

```python
def build_opening(mem, ltm, conversation_id: str, *, enabled: bool,
                  client_factory, native_lang: str = "") -> dict:
    """返回 {"enabled": bool, "resume": dict|None, "candidates": list, "notices": list}"""
def compile_memory_brief(items: list[dict], native_lang: str = "") -> str: ...
```

`build_opening` 的步骤：
1. `enabled=False` → 返回 `{"enabled": False, "resume": None, "candidates": [], "notices": []}`，不扫描，也不读任何东西。
2. `prev = mem.previous_session(conversation_id)`。
3. **续接**：`prev` 存在、`prev["scene_id"]` 非空、`get_scene(scene_id)` 能命中 → `resume = {"scene_id", "title", "title_zh", "conversation_id": prev["session_id"]}`；否则为 None。不调 LLM。
4. **扫描**：`prev` 存在且 `memory_scanned_at` 为空 → 取 prev 的 user 消息，`should_extract` 为真时调用 `client_factory()` 拿 client 再提取；每条结果走 `ltm.add_candidate("life_event", content, {"conversation_id": prev_id, "extractor": EXTRACTOR_VERSION, "event_key": f"{prev_id}:{i}"})`。单条 `LongTermMemoryError` 只跳过这一条。不管提没提到东西、`should_extract` 真还是假，最后都要调用 `mark_memory_scanned(prev_id)`，保证同一段只扫一次。`client_factory()` 返回 None（没有可用 provider）时**不标记**，加上 notice `{"stage":"memory_extract","reason":"no_provider"}`；提取抛异常时同样不标记，notice reason 为 `"extract_failed"`。
5. `candidates = ltm.list_items("candidate")`，返回时只保留 `memory_id, kind, content, created_at`，不带 source。

`compile_memory_brief`：
- items 为空 → 返回 `""`。
- 中文段落头 `[Memory] 学习者确认过的个人经历（可在合适时自然提起，用来引出练习话题；不要逐条复述，不要追问隐私，不要当作考题）：`，下面每条 `- {summary}`（有 place/when 时括号附上）。英文按同样语义翻译，段头是 `[Memory]`。

### 召回注入（`dialog_run._assemble_directives`）

- 读 `profile.memory_enabled`（缺失时视为 True）。为 True 时调用 `LongTermMemory(learner_id, root=mem.root).recall("life_event", limit=5)`，再 `compile_memory_brief`，结果放进返回字典的 `"memory_brief"` 键；为 False 或任何异常 → `""`。异常时追加 notice `{"stage":"memory_recall","reason":"recall_failed","fatal":False}`，沿用现有 notices 通道，Codex 选一个已有的汇入点，在日志里说明。
- 只在每段对话的**第一轮**（`history` 为空）注入。后续轮次靠对话历史延续，不重复注入，也避免 `recall_count` 每轮都涨。
- `planner.run(..., memory_brief=...)`；`_build_system` 在 `persona_brief` 之后、`style_directive` 之前追加。参数默认 `""`，不影响现有调用。

### HTTP（`serve.py`）

learner 的解析沿用现有路由的写法：`qs/payload["learner"]`，没有就用 `_router.learner_id`。

| 方法 路径 | 请求 | 响应 |
|---|---|---|
| `POST /api/memory/opening` | `{"conversation_id"}` | `build_opening` 的返回值。`client_factory` 用和 `/api/dialog` 默认供应商相同的解析方式，构造 `LLMClient(config=...)`；没有供应商返回 None |
| `GET /api/memory` | `?status=` 可选 | `{"items":[{memory_id,kind,status,content,created_at,confirmed_at}]}`，不带 source、dedup_key |
| `POST /api/memory/confirm` / `reject` / `forget` | `{"memory_id"}` | `{"memory_id","status"}`；actor 固定为 `"learner"`。`LongTermMemoryError` → 400 `{"error": str}`；不存在的 id 也返回 400 |
| `POST /api/profile` | 新增顶层 `memory_enabled: bool` | 非 bool → 400；部分合并语义和现有字段一致。`GET /api/profile` 透传该字段，缺失时为 true |

**改法：**

- `src/engine/memory/learner_memory.py`：
  - 按契约扩展 `touch(..., bump=True, scene_id=None)`；仅当 `scene_id is not None` 时写入，截断 80 字符，`bump=False` 时不改变 `updated_at`。
  - 新增 `previous_session(exclude_session_id)`：始终带当前 `learner_id`，排除当前会话，只选择至少含一条 `user` 消息的会话，按 `updated_at DESC, session_id ASC` 取一条并返回契约五个字段。
  - 新增 `mark_memory_scanned(session_id)`：写当前时间到 `memory_scanned_at`，不更新 `updated_at`；所有异常由上层开场编排捕获，不能阻断对话。
- `src/engine/memory/extractor.py`：新建会后提取模块。`should_extract()` 用确定性第一人称经历/时间/去向/计划正则筛选，覆盖卡片要求的正反例；`extract_candidates()` 只取最后 20 条 user 文本、每条截断 200 字，组装禁止推断和敏感信息的结构化 prompt，调用 `client.chat_json_strict()`，捕获 `JSONStrictError` 及其他异常返回 `[]`。后置过滤仅保留 `CONTENT_FIELDS["life_event"]` 字段、非空 summary，最多 3 条，并让 summary 符合 ≤40 字约束。
- `src/engine/memory/opening.py`：新建开场编排深模块：

  - 上一会话未扫描时读取其 user 消息；规则命中后调用 `client_factory()`。无 provider 返回 `no_provider` notice 且不标记；提取异常返回 `extract_failed` notice 且不标记；成功、无命中或提取到空列表均调用一次 `mark_memory_scanned()`。每个候选独立调用 `add_candidate("life_event", ...)`，单条失败跳过。
  - 返回候选只投影 `memory_id/kind/content/created_at`，不暴露 source；`compile_memory_brief()` 只把已确认条目的 summary 及可选 place/when 编译成中英文 `[Memory]` 段。
- `src/engine/dialog_run.py`：让 `_assemble_directives` 接收当前 history；读取 `profile.memory_enabled`（缺失按 True），且仅在首轮 history 为空时创建 `LongTermMemory`、召回最多 5 条 `life_event` 并编译 `memory_brief`。关闭或异常时传空串，异常通过现有 notices 通道追加 `memory_recall/recall_failed/fatal=False`，不阻断对话。每轮写回后若 `ctx["scene_id"]` 非空，以 `touch(..., scene_id=..., bump=False)` 保存，失败静默降级。将 `memory_brief` 传给 planner。

- `src/engine/serve.py`：
  - 新增 `/api/memory/opening`，按现有 learner 解析方式取学习者和 conversation_id，读取 profile 开关，在共享锁内调用 `build_opening()`。client factory 使用与 `/api/dialog` 相同的默认 provider 解析；因为现有 `LLMClient` 通过 `chat_json_strict(..., config=...)` 接收 provider 配置，计划使用一个本文件内的轻量配置适配器，不修改 `LLMClient` 构造函数。

**疑问与假设：**
- 任务卡文字写作“构造 `LLMClient(config=...)`”，但当前 `LLMClient.__init__` 不接受 `config`，配置实际由 `chat_json_strict(..., config=...)` 接收。方案假设不改卡片契约和 `LLMClient` 文件，而在 `serve.py` 的 `client_factory` 返回一个只转发 `chat_json_strict` 并注入 provider config 的适配器；如 Claude 要求直接构造式配置，需要先回写契约。
- `chat_json_strict` 当前返回 dict，但测试替身可能返回 list；提取器会兼容两者，只接受最终 list 项，不改变对外 `extract_candidates` 返回 list 的契约。
- 开场扫描成功后无论 `should_extract` 是否命中、候选是否为空，都标记已扫描；仅无 provider 或真正异常不标记，以满足“同一段只扫一次”和失败可重试的同时约束。
- `/api/profile` 的“透传 memory_enabled”按现有 profile 形状实现为 `profile["memory_enabled"]`，缺失时只在响应中补 true，不额外制造顶层字段。
- `memory_brief` 的 notice 汇入 `_writeback_round` 返回的 `notices`，这样沿用现有 `degraded`/响应通道；若执行时发现当前响应组装点不保留该列表，应在“问题与阻塞”提出，不自行扩展响应契约。

**风险：**
- 旧 `coach.db` 的 sessions 迁移若只加一列或迁移顺序错误，会使开场查询失败；需要专门覆盖旧 schema 和新 schema 两条路径。
- 候选提取使用 provider 的真实 LLM，提示词若把 assistant 内容混入或后置过滤过宽，会把推断写成 candidate；测试必须记录发送给 fake client 的完整 user 内容并断言无 assistant 文本。
- `mark_memory_scanned` 时序错误会导致每次开场重复调用 LLM，或失败后永久跳过重试；M1 和 opening 双调用测试必须锁定这两个分支。
- 召回若未限制首轮或未过滤 confirmed，会增加 recall_count、把候选当事实注入 planner；M2/M6 与首轮/第二轮测试必须分别失败后再还原。
- HTTP 路由沿用当前 learner 参数模型，单机阶段可接受，但部署到多用户环境前必须补身份隔离；本卡不扩展鉴权。
- `scene_id` 持久化失败不应阻断当前对话，但会降低下一次 opening 的 resume 能力；应通过失败注入测试确认主链仍返回成功。
