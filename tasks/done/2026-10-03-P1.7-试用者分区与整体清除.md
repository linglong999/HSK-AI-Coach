# [P1.7] 试用者专属分区、服务试用模式与整体清除

**状态：** 通过

**规模：** 大
**上游依据：** `reports/2026-09-30-后续迭代架构设计与任务编排.md` §13「P1 遗留 ②」；`tasks/done/2026-10-02-P1.6-复述目标关联.md`「遗留问题 3」；`reports/2026-09-30-A1-试用协议.md`「保存、退出与删除」；`DECISIONS.md` ADR-0013（本卡决策）
**依赖：** 无（P1.6 已提交 `e6ca94c`）

## 目标

邀请留学生（P2）之前，解决最后一项数据边界问题，并修复调研中新发现的接入缺口：

1. **原文无法整体删除**：试用对话的原文散落在会话记忆（messages/sessions）、事件账本（ledger_events.evidence）、画像（profiles）、图谱文件（片段与含原句的幂等键）和评分文件里。试用表只存会话引用的单向哈希，无法反查。图谱还是**整个进程共用一份**（`router.graph`），试用者的数据会和作者自己的数据累加在一起，事后拆不开。
2. **（新发现）网页聊天根本不会记录 A1 事件**：React 前端从不发送 `study_session_id`，P1 的记录机制只有直接调用 API 时才会生效。

**方案**（用户 2026-10-03 拍板）：每个试用者绑定一个专属的匿名学习者 `a1-xxxx`，所有数据只落在这个分区里；服务用 `--study <编号>` 以试用模式启动，服务端自动给每轮对话带上试用编号，前端不用改；撤回和清除分成两步，`purge` 要在服务停止后执行，一次清空整个分区。

前提事实（已核实）：前端不传 `learner_id`，所以一个服务进程实际只服务一个学习者，也就是 `router.learner_id`；记忆、账本、画像、评分都按 `learner_id` 分区，图谱文件按进程的 learner 命名（`graph_<learner>.json`）。

## 契约（R2：必须逐字照办）

### C1. 表结构

- `_SCHEMA` 中 `study_sessions` 增加一列：`learner_id TEXT NOT NULL DEFAULT ''`。
- `connect()` 中仿照 `completion_reason` 的写法：先用 `PRAGMA table_info(study_sessions)` 检查，缺 `learner_id` 列时执行 `ALTER TABLE study_sessions ADD COLUMN learner_id TEXT NOT NULL DEFAULT ''`；然后**在 `connect()` 中**（不放进 `_SCHEMA`）执行 `CREATE INDEX IF NOT EXISTS idx_study_sessions_learner ON study_sessions(learner_id)`。（2026-10-04 方案审查修订：索引写在 `_SCHEMA` 里时，旧库会在补列之前就执行建索引而失败。）

### C2. 试用学习者 ID

- 格式：`^a1-[A-Za-z0-9_-]{1,60}$`，在 `study.py` 中定义为模块常量 `STUDY_LEARNER_RE`。
- 自动生成：`"a1-" + secrets.token_hex(8)`。

### C3. `create_session` 绑定学习者

```python
def create_session(self, protocol_version: str = PROTOCOL_VERSION,
                   scene_type: str = "general",
                   learner_id: Optional[str] = None) -> str
```

- `learner_id` 为 None 或空串时，自动生成新的学习者 ID。
- 给定的 `learner_id` 不符合 C2 格式 → 抛 `StudyError`。
- **新分区检查**：如果 `study_sessions` 中还没有任何一行绑定这个 `learner_id`，而 `learner_data_counts(learner_id)`（C4）显示该学习者已有任何数据 → 抛 `StudyError("该学习者已有非试用数据，不能绑定为试用分区")`。已经绑定过的学习者（同一个试用者参加第二个场景）允许继续绑定。
- 绑定结果写入 `study_sessions.learner_id`。`status()` 和 `export_summary()` 的每个会话都要包含 `learner_id` 字段。
- `DialogService.study_create` 从 payload 读取可选的 `learner_id` 并透传，返回 dict 增加 `"learner_id"`。参数不合法时沿用现有的 400 `invalid_study_session`。

### C4. 学习者数据盘点

```python
def learner_data_counts(self, learner_id: str) -> dict
```

返回：

```python
{"learner_id": str,
 "ledger_events": int, "sessions": int, "messages": int, "profiles": int,
 "study_sessions": int,
 "files": list[str]}   # 已存在的文件名（只写文件名，不写路径），升序
```

前四项按 `WHERE learner_id=?` 计数，`study_sessions` 统计绑定了该学习者的行数。需要检查的文件（相对 `self.root`）固定为：`graph_<L>.json`、`graph_<L>.json.tmp`，以及 `engine.metrics._file(self.root, "feedback", L)` 指向的评分文件。

### C5. 整体清除

```python
def purge_learner(self, learner_id: str, force: bool = False) -> dict
```

**前置条件**，任一不满足就抛 `StudyError`，并且**不删除任何东西**：
1. `learner_id` 符合 C2 格式（防止误删作者自己的 `demo` 等分区）；
2. 至少有 1 行 `study_sessions` 绑定该学习者；
3. 绑定该学习者的所有会话，状态都不在 `{"consented", "active"}` 中（必须先撤回或结束）；
4. `force` 为 False 时，活动标记（C6）不存在。

**执行**：
- 在**一个 SQLite 事务**里依次删除 `ledger_events`、`messages`、`sessions`、`profiles` 中 `learner_id=?` 的行，再删除绑定该学习者的 `study_sessions`（`study_consent` 和 `study_events` 靠外键级联删除，删除前先统计 `study_events` 的数量）。提交之后再删除 C4 列出的文件。
- 单个文件删除失败不回滚数据库，把文件名记进 `file_errors`。

返回：

```python
{"learner_id": str,
 "deleted": {"ledger_events": int, "messages": int, "sessions": int, "profiles": int,
             "study_sessions": int, "study_events": int},
 "deleted_files": list[str], "file_errors": list[str],
 "not_covered": ["backups"]}
```

清除成功后，`learner_data_counts(L)` 的各项计数必须全为 0，`files` 为空。

（2026-10-04 方案审查补充）活动标记不算分区数据，不计入 C4 的 `files`。`force=True` 的含义是「操作者确认服务已经停止，标记是残留的」，因此 force 清除成功后要调用 `clear_active(self.root, L)` 删除残留标记；非 force 清除不涉及标记。

### C6. 活动标记（运行中的服务禁止被 purge）

`study.py` 中新增三个模块级函数：

```python
def mark_active(root: str, learner_id: str, study_session_id: str) -> str   # 返回标记文件路径
def clear_active(root: str, learner_id: str) -> None                        # 文件不存在时不报错
def is_active(root: str, learner_id: str) -> bool
```

标记文件为 `<root>/a1_active_<learner_id>.json`，内容是 `{"learner_id", "study_session_id", "started_at"}`。**不要**用进程 ID 判断存活（Windows 上 `os.kill` 会直接终止目标进程）。

### C7. `delete` 与 `list_expired`

- `delete(study_session_id)`：如果该会话绑定的学习者仍然有数据（C4 中任何计数大于 0，或 `files` 非空；`study_sessions` 那一项不算），抛 `StudyError("该试用者分区仍有数据，请先执行 purge")`。避免先删掉试用记录后，分区失去绑定、再也无法 purge。
- `list_expired` 的每一项增加 `learner_id`，变为四个字段 `study_session_id`、`status`、`retention_until`、`learner_id`，排序规则不变。

### C8. CLI

- `create` 增加 `--learner-id`（可选）；输出 JSON 增加 `learner_id`。
- 新增 `inspect --learner-id L`：输出 `learner_data_counts(L)` 的 JSON。
- 新增 `purge --learner-id L [--force]`：输出 `purge_learner` 的 JSON。失败时向 stderr 输出错误信息，退出码为 2。
- `purge` 和 `inspect` 不使用位置参数 `study_session_id`。

### C9. 对话的学习者绑定检查（`DialogService.dialog`）

在现有的 `is_recordable` 检查之后、构造 DialogRun 之前，令 `bound = tracker.status(sid)["learner_id"]`。只要 `bound == ""`、`bound != ctx["learner_id"]`、`bound != self._router.learner_id` 三者有任意一个成立，就返回：

```python
400, {"error": "试用编号与当前学习者分区不一致", "code": "study_learner_mismatch"}
```

此时不能产生任何写入。

（2026-10-04 方案审查补充）允许把 `dialog()` 中整个试用检查块（`is_recordable` + C9 绑定检查）移到 `_consume_visitor_quota` 之前。现状是先扣游客额度再检查试用，被拒绝的回合也会被计数。移动后被拒绝的试用回合不再消耗额度，属于改进。「零写入」指学习者数据和额度的写入；SQLite 打开连接时的建表和迁移不算。

### C10. 服务端默认试用编号

- `DialogService.__init__` 增加关键字参数 `study_session_id: str = ""`，保存为 `self._default_study_session_id`。
- `_load_session_context`：从 payload 读出的编号记为 `sid`。如果设置了默认编号：`sid` 非空且与默认编号不同 → 返回 `400 {"error": "试用编号与服务试用模式不一致", "code": "study_session_mismatch"}`；否则令 `sid` 等于默认编号。
- `create_app` 增加关键字参数 `study_session_id: str = ""`，透传给 DialogService。

### C11. 服务试用模式（`serve.py`）

```python
def _resolve_study_mode(study_session_id: str, learner: Optional[str], root: str = "data") -> str
```

返回绑定的学习者 ID。以下情况抛 `ValueError`，消息为中文：编号不存在或不合法；状态不在 `RECORDABLE_STATES` 中；绑定的学习者为空；`learner` 非空并且与绑定的学习者不同。

`main()` 的改动：
- `--learner` 默认值改为 `None`，未指定时视为 `"demo"`。
- 新增 `--study`，默认值 `""`。给了 `--study` 时：调用 `_resolve_study_mode`（出错就 `ap.error(消息)`），用返回的学习者构造 Router，调用 `mark_active("data", learner, sid)`，`create_app(..., study_session_id=sid)`，并用 `try/finally` 包住 `uvicorn.run`，在 finally 里调用 `clear_active`。
- 没有 `--study` 时，行为与现在完全一致。

## 实现要点

- purge 直接在 `study.py` 里对同一个 `coach.db` 执行 SQL，不去改 `LearnerMemory` 或 `ErrorLedger`。这样做是为了让多表删除在一个事务里完成，保证原子性。表名和列名以 `store.py` 的 `_SCHEMA` 为准。
- `self.root` 就是 coach.db 所在目录，图谱文件和评分文件都放在它下面。生产环境里 root 是 `"data"`，图谱默认路径是 `data/graph_<L>.json`，两者一致。
- 绑定检查（C9）必须放在任何写入之前。识别预扫会写图谱，它在 DialogRun 里面，所以检查放在构造 DialogRun 之前就足够了。
- 旧数据兼容：`learner_id == ''` 的旧试用记录，在对话时会因为 C9 被拒绝，purge 时会因为 C5 第 2 条被拒绝（没有可清除的分区），用 `delete` 删除即可。真实库中试用表目前是 0 行。
- **既有测试**（Claude 已核实会受 C9 影响）：`DialogSmokeBase` 的 `FakeRouter.learner_id` 是 `"smoke-learner"`，不符合 `a1-` 格式，而 `create_session()` 会自动生成另一个学习者。因此 `tests/test_study_flow.py` 的 `StudyFlowTest` 和 `tests/test_dialog_run_smoke.py` 的 `StudyIntegrationTest` 在 C9 之后会返回 `study_learner_mismatch`。**只允许**做以下修改，所有断言不得修改：
  - 在这两个测试类中覆盖 `setUp`：先调用 `super().setUp()`，然后 `self.router.learner_id = "a1-smoke"`，接着**立刻**调用 `self.svc.get_study_tracker().create_session(learner_id="a1-smoke")` 建立一条绑定（返回值可以不用）。必须在任何对话之前先绑定，因为 `test_no_study_reference_is_lazy_and_patch_positive_control` 会先跑一轮非试用对话、之后才创建试用，如果那时分区还没绑定，就会被 C3 的新分区检查拒绝。
  - 这两个类里所有调用 `create_session(...)` 的地方都加上 `learner_id="a1-smoke"`。
  - `test_unconsented_session_returns_400_and_records_nothing` 预期不受影响：`is_recordable` 检查在 C9 之前执行。
  - `tests/test_dialog_run.py` 直接构造 DialogRun，不经过 C9，不需要修改。
  - 按以上方式修改后，如果仍有既有测试失败，写入「问题与阻塞」后停下。
- 新测试中凡是要走对话的，router 的 `learner_id` 都用 `a1-` 格式，写法同上。

## 实施方案（Codex 计划对话填写，动代码之前）

**改法：**
- `src/engine/memory/store.py`：在 `study_sessions` 新表定义加入 `learner_id TEXT NOT NULL DEFAULT ''`；`connect()` 先用 `PRAGMA table_info` 检查旧库，缺列时执行 `ALTER TABLE`，再创建 `idx_study_sessions_learner`，保证旧表不会在列迁移前因建索引失败。迁移后保持 `foreign_keys=ON`，不改其他表和现有遗留 JSON 迁移逻辑。
- `src/engine/study.py`：增加 `STUDY_LEARNER_RE`、`a1-` 自动 ID 生成和 `create_session(..., learner_id=None)` 绑定流程。先校验格式，再通过 `learner_data_counts()` 检查未绑定的新分区是否已有账本、会话、消息、画像或图谱/评分文件；已有绑定的同一学习者允许新增场景。`status()`、`export_summary()`、`list_expired()` 补充 `learner_id`，并保持过期严格 `< now` 和原排序。
  - 新增 `learner_data_counts(learner_id)`：在同一 `coach.db` 中按 `learner_id` 统计 `ledger_events`、`sessions`、`messages`、`profiles`、`study_sessions`，并调用 `engine.metrics._file(root, "feedback", learner_id)`，联合检查 `graph_<L>.json`、`.tmp` 和评分文件，只返回文件名升序列表。
  - 新增 `purge_learner(learner_id, force=False)`。先完成全部前置检查：`a1-` 格式、至少一个绑定会话、所有绑定会话均不在 `consented/active`、非 force 时不存在活动标记；任一失败立即抛 `StudyError`，不执行 SQL 删除或文件操作。通过后在同一个 SQLite 事务内预先统计待删数量，严格依次删除 `ledger_events` → `messages` → `sessions` → `profiles` → `study_sessions`；依赖外键级联删除 `study_consent/study_events`，提交前统计 `study_events` 数量。SQL 异常统一回滚，不触碰文件。事务提交成功后，再逐个删除 C4 文件；单个 `OSError` 只记录文件名到 `file_errors`，不回滚数据库，返回 `deleted_files`、`file_errors` 和 `not_covered=["backups"]`。不把活动标记计入分区数据盘点或返回文件列表。

**风险：**
- 旧 SQLite 表迁移、索引创建和外键级联若顺序错误，可能导致启动失败或漏删子表；必须用旧库迁移测试和事务失败测试验证。
- purge 的 SQL 删除已提交后无法因文件失败回滚，可能留下图谱/评分文件；`file_errors`、盘点和人工重试必须保持可见，备份始终不在范围内。
- `force=True` 允许活动标记存在时清除，若服务仍在运行，内存中的图谱/缓存可能在 purge 后再次写回文件；活动标记是协作式保护，不能替代进程隔离或 PID 锁。

- `learner_id` 虽然经过格式校验，仍需确保所有图谱/评分路径使用同一安全命名规则；本卡不修改 `metrics.py`、`ErrorGraph`，因此命名规则漂移是持续维护风险。
