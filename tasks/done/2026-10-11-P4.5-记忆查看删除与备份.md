- 缺口一：遗忘只把那一行的 content 清空。SQLite 默认不覆盖已释放的页，原文字节可能留在库文件里，随下一次备份带走。Claude 做过一次探针，没有复现残留，但这一点不能保证。
- 缺口二：从遗忘之前的备份恢复，被遗忘的记忆会回来。ICO 关于删除权的指引认为，备份里的数据只要"不再使用"就可以接受，但恢复时必须重新执行删除（[ICO Right to erasure](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/individual-rights/individual-rights/right-to-erasure/)）。

## 契约

```text
python -m engine.memory.long_term forget-all --learner-id X [--root data]
  → 对该 learner 所有非 forgotten 条目执行 forget(actor="operator")
  → stdout: {"learner_id": X, "forgotten": n}

python -m engine.memory.long_term reapply-forgets --learner-id X --from <当前data目录> [--root <恢复出的目录>]
  → 读 --from 库里该 learner 的 forgotten 墓碑 memory_id 集合；
    在 --root 库里，对同 learner、同 memory_id 且状态不是 forgotten 的条目执行 forget(actor="operator")
  → stdout: {"learner_id": X, "reapplied": n, "missing": m}   # missing = 墓碑在 --root 中不存在的个数
  → --from 与 --root 解析后是同一路径 → 退出码 2
```

- `secure_delete=ON` 放在 `ensure_store` 建立连接后，和 `journal_mode=WAL` 一起执行。
- 两个新命令的错误一律走现有 `LongTermMemoryError` → stderr、退出码 2；不打印记忆内容。
- `reapply-forgets` 只读 `--from`，用 `mode=ro` URI 打开，绝不写入。

1. **`store.py`：** 在 `connect` 建立连接后、与现有 `journal_mode=WAL` 相邻处执行 `PRAGMA secure_delete=ON`，使 `ensure_store` 的所有调用方在建表、迁移及写入前获得设置；不改 schema、不追溯擦除历史空闲页、不增加自动 checkpoint/VACUUM。复用现有连接配置及 `LongTermMemory.forget` 清空 content/source、保留墓碑的语义。
2. **`long_term.py`：** 扩展现有 `_main` 命令枚举及 `--from` 参数，保留 list/forget 行为；forget-all 从该 learner 的 `list_items()` 快照筛选非 forgotten，逐条 `forget(actor="operator")`，按契约输出计数。reapply-forgets 在创建目标 `LongTermMemory` 前解析两目录及 `coach.db` 路径，拒绝同路径（兼顾 Windows 大小写、符号链接及同一数据库文件别名）、缺少 `--from`、不存在/无效源库或恢复库；源连接独立用 `Path.as_uri() + "?mode=ro"`、`uri=True` 打开，绝不调用源库的 `ensure_store`、迁移或写入 PRAGMA，只用参数化 SQL 读取指定 learner 的 forgotten memory_id。目标复用 `get/forget`：同 learner 不存在计 missing，已 forgotten 不计 reapplied，其余成功遗忘才加一；无源墓碑输出两个 0。文件/SQLite 错误转换为不包含记忆内容的 `LongTermMemoryError`，沿现有 stderr/退出码 2 处理，失败不输出成功 JSON，所有连接 finally 关闭；每条 forget 自行 commit，发生部分成功时不宣称整体回滚。
3. **`tests/test_long_term_memory.py` 仅追加：** 在临时真实库验证连接设置、forget-all 对 candidate/confirmed/rejected/forgotten 的计数、重复为 0、operator 身份和 learner 隔离；通过 `_main` 验证两个新命令的精确 JSON、missing/已 forgotten/空墓碑计数及错误退出，覆盖相对路径别名相等、源库缺失/损坏且不生成新库、跨库同 memory_id 属于不同 learner 时不得遗忘。字节演练用恰好 200 字的唯一 ASCII 标记（满足 summary 上限和本卡 ≥200 字），只存于长期记忆、不另存 messages，确认后先证明标记确实存在，再遗忘、检查 `wal_checkpoint(TRUNCATE)` 成功且无 busy，扫描 coach.db 及存在的 -wal 并验证 recall/get 不含原文；独立同构临时库关 secure_delete 重做反例，若无法复现残留按卡片记录页布局/SQLite 环境，不伪造反例通过、不改旧测试。
4. **`tests/test_local_backup.py` 仅追加：** 不复用 `_source` 的简化 sessions 表来初始化 `LongTermMemory`，另建真实 schema 的临时目录；复用 `create_backup/verify_backup/restore_backup`，验证遗忘及 checkpoint 后的新备份全部文件无标记。完成“含 confirmed 的备份 A → 当前库遗忘 → 恢复到不存在的新目录 → 仍 confirmed → CLI 重放 → forgotten、内容清空、recall 排除、reapplied=1”的演练，另一个 learner 保持不变；源库停写并预先 checkpoint，命令前后比较 coach.db SHA-256，同时检查已有 -wal 的字节变化，避免只查主库漏掉 WAL 写入。执行对话再运行全量 pytest、deterministic 和本卡两文件定向测试，逐一做 M1–M3、记录真实失败数及生产代码还原证据；不改 `local_backup.py`、DEPLOYMENT、前端或真实 data。
5. **疑问与假设、风险：** 契约称设置放在 ensure_store，现有实际配置点是它调用的 connect，以上按“建立连接后且与 WAL 一起”放 connect，不另造连接路径；恢复目标假设必须是既有恢复库，禁止拼错目录时静默建空库。secure_delete 不清聊天记录中的独立副本、旧备份、历史 WAL 或存储设备快照，字节验收限定本次配置生效后写入/遗忘且成功 checkpoint 的测试数据；恢复库在重放完成前不得供应用使用。M1 若环境 SQLite 默认 secure_delete 已为 ON，单独删除配置可能仍全绿；与 OFF 反例无法复现一样须据实记录并请 Claude 明确突变验收方式，不能擅自把 ON 默认改成 OFF 冒充 M1，或削弱正向字节断言。源库主文件哈希不变也不等于 mode=ro 绝无 WAL/SHM 辅助文件行为，不用 immutable 跳过可能尚在 WAL 中的墓碑；操作按停服务演练，墓碑被 purge 后无法重放的边界仍留文档说明。本次只交方案，小卡状态保持待开工，不实施、不运行测试、不提交。
