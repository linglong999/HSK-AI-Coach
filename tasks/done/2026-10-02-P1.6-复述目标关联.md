## 目标

修复主闭环「讲解 → 复述检验 → 沉淀复习计划」的断点。现状有三层问题，根因相同：**复述验证时系统不知道这次复述对应哪个知识点**。

1. **图谱收不到复述结果**：`skills/verify_retell.py` 调用 `Verifier.verify` 时不传 `bias_ref`，而 `Verifier._wrap` 只在 `bias_ref is not None` 时调用 `graph.ingest_verdict`。复述通过不会提升掌握度，失败也不会累计 `unfixed_streak`（化石化依据）。`DialogService._writeback_ledger_events` 的 docstring 声称「verify→ingest_verdict 已在技能内完成」，与事实不符。
2. **账本确认靠猜**：复述 pass 时，确认本轮全部识别的 KP，或者账本里最近 3 个未确认的 KP。一次复述可能确认多个知识点。
3. **A1 学习事件不带知识点**。

本卡引入由编排层确定性维护的**复述目标**（retell target），用它统一驱动上面三处写入。

## 契约（R2：必须逐字照办）

### C1. 复述目标的数据形态

```python
# 复述目标（retell target）：dict 或 None
{"kp_id": str,          # 非空
 "fragment": str,       # 可为 ""
 "type": str,           # 可为 ""
 "uncertain": bool,
 "set_in_round": bool}  # 仅用于本轮内部判断，存入会话缓存前必须置为 False
```

### C2. 会话缓存与注入

- `DialogService.__init__` 新增 `self._retell_state = {}`，结构为 `conversation_id -> {"current": target | None}`。
- 新增 `DialogService._get_retell_state(conversation_id) -> dict`，写法照抄 `_get_meta_ask`：不存在就创建 `{"current": None}`，返回同一个 dict 对象。
- `DialogRun.__init__` 新增关键字参数 `retell_state=None`，保存为 `self._retell_state = retell_state if retell_state is not None else {"current": None}`。
- `DialogService.dialog` 构造 DialogRun 时传入 `retell_state=self._get_retell_state(ctx["conversation_id"])`。

### C3. 目标解析算法：`DialogRun._apply_retell_outcomes(self, trace, pre, conversation_id) -> list[dict]`

先构造**合法 KP 集合** `K`，取以下各项的并集：
- `pre["pre_scan"]["errors"]` 里各项的 `knowledge_point_id`（`pre_scan` 是 dict 时才取）；
- trace 中 `ok` 为真的 `identify_errors` 项，其 `result["errors"]` 里各项的 `knowledge_point_id`；
- `self._deep_dived_kps`；
- 进入本轮时 `self._retell_state["current"]` 的 `kp_id`（如果有）。

然后令 `current = self._retell_state["current"]`，按 trace 顺序逐项处理：

1. **`explain_error` 项**（`ok` 为真）：取 `params["error"]`。如果它是 dict，且 `knowledge_point_id` 非空并属于 `K`，则令 `current = {"kp_id": …, "fragment": error.get("fragment") or "", "type": error.get("type") or "", "uncertain": bool(error.get("uncertain", False)), "set_in_round": True}`。不满足条件就忽略，`current` 不变。
2. **`verify_retell` 项**：取 `result["verdict"]`。如果不在 `{"pass", "partial", "fail"}` 中，跳过。否则用当前的 `current` 作为本次目标，按 C4 处理并追加一条结果；如果 verdict 是 `pass` 或 `fail` 且目标存在，处理完后令 `current = None`（目标已消费）。`partial` 不消费目标。

trace 处理完后：
3. **（2026-10-02 方案审查时修订）** 如果 `current` 为 None，或者 `current["set_in_round"]` 为 False，令 `s = pre.get("strategies") or {}`，按以下顺序**只取第一条命中**：
   - a. `s.get("deep_dive")` 是带非空 `knowledge_point_id` 的 dict → 按第 1 步的格式用它构造 `current`（`set_in_round=True`）；
   - b. 否则，取 `s.get("light_marks") or []` 中各项非空 `knowledge_point_id` 的**去重集合**。集合恰好有 1 个元素时，用该 mark 按第 1 步的格式构造 `current`（`set_in_round=True`；同一 KP 有多个 mark 时取第一个）；
   - c. 否则，如果该集合有 ≥ 2 个元素 → `current = None`。本轮呈现了多个知识点，下一轮的复述对象有歧义，宁漏勿错；
   - d. 否则（本轮没有呈现任何反馈）→ `current` 保持不变。

   修订原因：只有 block 档会产生 deep_dive，none 和 light 档只产生 light_marks（已实测 `select_feedback_strategies`）。只看 deep_dive 的话，最常见的「流利地写出一句病句」场景永远不会有复述目标。
4. 如果 `current` 不为 None，把 `set_in_round` 置为 False。然后写回 `self._retell_state["current"] = current`。

返回值是按 trace 顺序排列的结果列表，每一项为：

```python
{"index": int,              # 该 verify_retell 在 trace 中的下标
 "verdict": str,
 "covered_points": int, "total_points": int, "degraded": bool,   # 取法同 P1-fix C3
 "kp_id": str,              # 无目标时为 ""
 "target_source": str,      # "same_round" | "previous_round" | "none"
 "graph_applied": bool}
```

`target_source` 的取值：目标的 `set_in_round` 为 True 时取 `"same_round"`，为 False 时取 `"previous_round"`，没有目标时取 `"none"`。

### C4. 对每条复述结果的写入规则

| verdict | 有目标 | 无目标 |
|---|---|---|
| `pass` | 图谱 `ingest_verdict(verdict="pass")`；账本 `wb.on_confirmed(kp_id, evidence="复述验证通过")` | 什么都不写 |
| `fail` | 图谱 `ingest_verdict(verdict="fail")`；账本不写 | 什么都不写 |
| `partial` | 图谱、账本都不写 | 什么都不写 |

图谱调用必须严格写成：

```python
self._router.graph.ingest_verdict(
    bias_ref={"knowledge_point_id": t["kp_id"], "fragment": t["fragment"], "type": t["type"]},
    verdict=verdict, uncertain=t["uncertain"],
    event_key=f"retell:{conversation_id}:{t['kp_id']}:{digest}")
```

其中 `digest = hashlib.sha256(restatement.encode("utf-8")).hexdigest()[:16]`，`restatement = str((item.get("params") or {}).get("restatement") or "")`。

- `graph_applied`：`ingest_verdict` 正常返回、且返回 dict 的 `status` 不等于 `"idempotent_skip"` 时为 True；返回 `idempotent_skip` 或抛异常时为 False。（2026-10-02 方案审查时修订：幂等跳过意味着图谱实际没有变化，A1 事件应当如实反映。）
- 本轮只要有任何一次 `ingest_verdict` 被调用，就在 `_apply_retell_outcomes` 末尾调用一次 `self._router.graph.save()`。
- 图谱写入、图谱保存、账本写入，每一项各自 try/except。失败时把 `{"stage": "retell_writeback", "reason": "retell_writeback_failed", "fatal": False}` 加入本轮 notices（同一种失败只加一次），不阻断对话。

### C5. 调用位置

`_apply_retell_outcomes` 在 `_writeback_round` 内调用，紧接在 `self._writeback_ledger_events(...)` 之后、`self._observe_uptake()` 之前。这样采纳观测能看到本轮的 `concept_confirmed`。`_writeback_round` 的返回 dict 增加键 `"retell_outcomes"`，值为 C3 的返回列表。

### C6. `_writeback_ledger_events` 与 `_unconfirmed_recent_kps`

- `_writeback_ledger_events` **签名不变**。删除 `elif name == "verify_retell" ...` 整个分支，只保留识别分支。docstring 改为如实描述：「只处理识别 → observation_error；复述确认由 DialogRun._apply_retell_outcomes 负责」。
- 删除 `DialogService._unconfirmed_recent_kps`（删除后已无调用方）。

### C7. A1 学习事件

`study.EVENT_FIELDS` 中三个学习事件（`learning_confirmed` / `learning_pending` / `learning_rejected`）的字段集合改为：

```python
{"conversation_ref", "verdict", "covered_points", "total_points", "degraded", "source",
 "kp_id", "target_source", "graph_applied"}
```

`_validate_payload` 新增以下校验：
- `kp_id`：str，长度 ≤ 120，允许空串；
- `target_source`：必须属于 `{"same_round", "previous_round", "none"}`；
- `graph_applied`：bool。

`DialogRun._emit_study_learning_result` 改为读取 `wb_out["retell_outcomes"]`，不再自己遍历 trace。事件类型映射、`source="verify_retell"`、`event_key=f"learning_result:{index}"` 保持不变，payload 补上三个新字段。事件顺序与 P1-fix C5 一致。

## 实现要点

- **复述目标为什么要这样解析**：深攻 1（`strategies["deep_dive"]`）的定义就是「显式精讲 + 引导复述」，所以它是策略层确定性指定的复述对象。`explain_error` 的入参由 LLM 填写，因此必须用集合 `K` 校验，防止 LLM 编造 KP。本轮的 deep_dive 只能作为**下一轮**的目标，不能用于本轮的复述，因为本轮的复述针对的是上一轮讲过的内容（见 C3 第 3 步的时序）。
- `_deep_dived_kps` 在 `_select_and_log_strategies` 中被更新，`_apply_retell_outcomes` 运行时它已经包含本轮的 deep_dive。
- **锁与缓存不变式**（`CONTEXT.md`）：缓存只归 DialogService 持有，DialogRun 只拿到注入的 dict 并原地修改；DialogRun 内部不加锁。
- **既有测试**（`tests/test_dialog_profile.py`）。注意：这个文件的假 router 中 `explainer = None`，如果 planner 真的调用 `explain_error`，会现场构造真实的 Explainer/LLM，结果不可控。**因此修改这两个测试时不要使用 `explain_error` 动作。**
  - `CrossRoundConfirmTest`：先不改，直接运行。按设计应当通过：第 1 轮预扫识别出 `kp-order-many`，介入档为 none，产生唯一的 light_mark（C3-3b），第 2 轮的复述以它为目标。
  - `VerifyConfirmLedgerTest`：现在的场景是「同一轮识别加复述，没有前置讲解」。按新规则这种情况没有目标，不会确认，测试会失败。**只允许**这样修改轮次设置：在 `_run_verify_round` 里，用同一个 `conversation_id`，先跑一轮只做识别的对话（照抄 `CrossRoundConfirmTest` 第 1 轮的 `_identify_round(...)` 加 `_post(...)` 写法），然后再跑原来的复述轮。断言（pass 确认 1 次、fail 不新增确认、`feedback_presented` / `uptake_observed` 存在）**不得修改**。
  - 如果按上述方式修改后仍然失败（比如第 1 轮没有产生 deep_dive），写入「问题与阻塞」后停下，不要另想办法。任何其他既有断言需要修改时也一样。
- **新测试的写法**：`tests/test_retell_target.py` 推荐在 DialogRun 或 DialogService 层用假 planner 直接返回构造好的 trace（`explain_error` / `verify_retell` 项都直接写成 dict，带 `"ok": True` 和 `params`），不实际运行讲解或验证技能。可以参考 `tests/test_study_flow.py` 中 `patch.object(planner, "run", ...)` 的做法。deep_dive 可以通过预扫的假识别结果自然产生，也可以 patch `_select_and_log_strategies` 的返回值来构造，两种都允许。
- `test_api_error_redaction.py` 和 `test_transfer.py` 直接调用 `_writeback_ledger_events`，传入的只有识别 trace，应当不受影响。

## 实施方案（Codex 计划对话填写，动代码之前）

**改法：**
- `src/engine/dialog_run.py`：在 `__init__` 增加关键字参数 `retell_state=None`，按 C2 保存注入的同一 dict 对象；不在 `DialogRun` 内加锁。新增 `_apply_retell_outcomes(self, trace, pre, conversation_id) -> list[dict]`，把目标解析、图谱写回和账本确认集中在一个深模块接口中。
  - 先构造合法 KP 集合 `K`：合并 `pre_scan.errors`、trace 中成功的 `identify_errors.result.errors`、`self._deep_dived_kps` 和进入本轮时缓存目标的 `kp_id`；只接受非空 `knowledge_point_id`。按 trace 原顺序维护 `current`：成功的 `explain_error` 只有在 `params.error` 为字典、KP 属于 `K` 时才替换当前目标，并记录 `fragment/type/uncertain` 与 `set_in_round=True`；每个合法 `verify_retell` 读取当前目标生成一条结果，`pass/fail` 消费目标，`partial` 保留目标，其他 verdict 跳过。
  - trace 完成后才处理 `pre["strategies"]["deep_dive"]`：仅当当前目标为空，或当前目标的 `set_in_round` 已为 False，且 deep dive 含非空 KP 时，才把它设为新的当前目标并标记 `set_in_round=True`。这保证本轮新选出的 deep dive 不会被本轮 verify 消费，而是作为下一轮的 `previous_round` 目标；随后把缓存目标的 `set_in_round` 置为 False，再写回 `self._retell_state["current"]`。返回列表严格按 verify 在 trace 中的下标排序，并补齐 `kp_id`、`target_source`、`graph_applied` 等字段。
