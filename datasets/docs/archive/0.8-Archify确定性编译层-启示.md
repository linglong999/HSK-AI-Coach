# 0.8 · 从 Archify 借鉴的确定性编译层原则

> **来源**：Archify（tt-a1i/archify，v2.16 · MIT · 超热门架构图 Agent）
> https://github.com/tt-a1i/archify
> **研读方式**：浅克隆到 `../archify-study/` 临时区，精读源码级（`archify/references`、`schemas`、`renderers`、`delta`），**未引入运行依赖**。
> **用途**：为"生成单元 schema v1 的确定性编译层"提供可移植样板 —— 呼应本项目"强 schema + JSON 自愈 + 轻依赖"铁律。
> **定位**：方法论参照，不是改造依据。Archify 是"代码架构图 → 渲染器"，本项目是"偏误教学回合 → 偏误图谱"，**共享编译层形态，领域不同**。

---

## 0. 一句话：它证明了什么

> **LLM 产出 typed JSON → 确定性编译 → 自包含交付**，是一条可规模化的可靠流水线。

Archify 让它产品化：Agent 产出 JSON IR（不可靠），Archify 用**确定性校验 + 确定性布局**编译成 HTML/SVG（可靠、可复现、可对比）。这和我们"LLM 判断 + 确定性图谱"是同一个哲学——**LLM 只做理解，确定性层保可复现**。

---

## 1. 六条可移植原则（按价值排序）

### P1 · Authoring Contract 与 Schema 分离、但互指
- Archify 把"教 Agent 怎么写"（`authoring-contract.md`）和"机器校验凭什么"（`schemas/*.schema.json`）**分成两个产物**；`$ref` 共享 `common.schema.json`。
- 取舍：contract 面向 LLM 的提示词，schema 面向校验器。**改 schema 必须同改 contract**，否则 Agent 产出与校验器脱节。
- 映射到本项目：`0.7-生成单元schema-v1.md` 相当于 schema；**下一个要补的是"给生成引擎的 authoring prompt"**——两者必须做到同一字段口径。
- ✅ **已落实（2026-08-31 · 见 0.15）**：`engine/generation/authoring.py` + `validator.py` 补齐 authoring prompt 与确定性校验器，字段口径与 schema 一致。

### P2 · 诊断按"稳定 code + exact subject + measured evidence + supportedFixes"
- Archify 的校验不笼统报错，每条问题是：稳定 `code`（可被代码/脚本引用）+ `subject`（精确对象）+ `evidence`（实测值）+ `supportedFixes`（可选修复方向），并给 `repair order`。
- 取舍：诊断**可被机器消费**，修复**可执行**，复议**可复跑**。这才是"可复现"的数据形态，不是人读的一行字。
- 映射到本项目：**偏误图谱的"复核/争议"记录也要有稳定状态码**（如 pending/confirmed/rejected 已定），并保留 `evidence` 字段说明"为什么这么判"。

### P3 · 修复有优先级（repair order）
- Archify 明确定序：**先 schema 错误 → 再节点重叠/越界 → 再边穿节点 → 再交叉/走廊 → 最后标签间距**。
- 取舍：**先修正确性，再修美观**。绝不为了过校验而删语义数据（"Deleting it is not a spacing repair"）。
- 映射到本项目：生成单元 JSON 自愈也要定序——先 schema 合法 → 再 keyPoints/forbidden_errors 语义完整 → 最后长度/结构优化。

### P4 · 语言一致性：一个主导 locale，不静默降级
- Archify 规则：选一个主导语言；`meta.locale` 只控制渲染器自有界面；**不支持的语言不写 locale、保持英文回退、并明确告知**；禁止静默替换成 zh-CN。
- 取舍：**"告诉用户极限"优于"偷偷降级"**——不撒谎、不越界。
- 映射到本项目：多语言（越/韩/日）走 `languageDirective` + `self_language`，同样应**不静默抹平**：不支持就明说，而不是含糊其辞。

### P5 · 证据与叙事分离（evidence ≠ 推断）
- Archify 严格区分"**authored 关系**"与"**推断的运行时影响/破坏**"——只有 `--repo-root` 实测过的才算证据；`reach` 的 receipt 只报节点/边/跳数，**绝不宣称"影响范围/破坏"**。
- 取舍：**宁可少声称，不可虚声称**——这正是本项目"宁漏勿错"在架构层的同构。
- 映射到本项目：偏误图谱里的"确认/待确认/驳回"三态，本质是"证据等级"而非语义断言。

### P6 · 确定性布局 + 自包含交付
- 布局是**确定性编译**（不是前端再跑一遍 force layout），且默认产物是**自包含 HTML/SVG**（无宿主运行时）。
- 取舍：**渲染 = 纯函数**，输入同一 JSON 永远同图 → diff 才有意义（Archify 的 `delta` 靠这点做 before/delta/after）。
- 映射到本项目：M10 前端壳的认知地图若也想"可对比、可回放"，**布局逻辑应放进确定性编译层（Python），而不是前端自由布局**。

## 2. 对 schema v1 的具体建议（三处校准）

1. **补 `authoring-contract`**：0.7 是 schema 本体，下一步给生成引擎这份 prompt 契约，字段口径与 schema 完全一致。
2. **给 `id` 加"证据字段"**：0.7 里 `id` 只做唯一标识；建议校验时**保留它的出处/状态**（呼应 P2 的 evidence）。
3. **`status` 进入后置单元的字段纪律**：dialogue/interactive/pbl 虽是 `*Spec?: null`，但一旦启用，**先定它的 validator + repair order，再写 renderer**（呼应 P3/P6 的"先正确后美观、先契约后渲染"）。

## 4. 一句话收束

> Archify 把"强 schema 的信任"做到了极致——**环路（contract→schema→validator→renderer→delta）每一环都确定性**。本项目不求全要，只取最贴合的 P1（contract/schema 分离）+ P2（稳定诊断码）+ P3（修复定序）三件套，足以撑起生成单元 v1 的确定性编译层。
