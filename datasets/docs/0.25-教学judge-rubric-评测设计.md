# 0.25 教学 Judge · Rubric 评测设计

## 一、背景与结论（为什么做、不用重学什么）

对 HSK-AI-Coach 与 OpenMAIC 的"教学文件设计"做三方对照（你的个人知识库方法论 × 行业评测框架 × OpenMAIC）后，结论如下：

- **OpenMAIC 唯一强于我们的部件**：把"教学质量标准"写成**可执行的 judge rubric + red line**（`eval/pbl-v2-planner/judge-prompt.md`，12 条评分维度 + 11 条 red line，输出 `{"pass":bool,"reason":"..."}`），且接入评测跑分，能自动回归。
- **我们的知识库方法论在 case 形态/分层/判分/指标/回流/独立性六个维度上打平甚至领先**（见《评测数据集构建.md》《Skill评估体系.md》《Badcase归因SOP.md》）。
- **真正的差距不是"方法论"，是"搬运"**：知识库里方法论已成型，但没落到 HSK 项目的可执行评测脚本；现在 `datasets/eval/` 缺成文的 HSK 领域 rubric、缺 judge 驱动器脚本、缺 pass^k 回归门槛、缺带"预期行为 + red line"字段的结构化 case。

因此本设计**不学习 OpenMAIC 的条目**，而是**把知识库三层评测方法论翻译成 HSK 领域的教学 judge**，Orthogonal 到现有黄金集资产上。

## 二、设计目标与边界

**目标**：改动（改 prompt/persona/技能/引擎）后，能自动回答"这次改没改坏教学质量"——用一个可复跑的命令，输出教学质量的 pass/fail + 逐维度分数 + red line 判定。

**明确不做（边界）**：
- 不评分"生成了多好的课"（那是 OpenMAIC 的场景）。我们评的是**逐次纠错/讲解/介入的教学质量**。
- 不做在线实时 judge（首版离线，学 OpenMAIC 的 eval 目录形态）。
- LLM-judge 永不独自做最终裁决，必须有人工 gold 校准（对齐行业最佳实践 + 你的知识库）。

## 三、目录结构与部件

参考你的《本地评测落地.md》骨架，落在现有 `datasets/eval/` 下：

```
datasets/eval/tutor_quality/
├── rubric.md                 # 成文 rubric：HSK 领域评分维度 + red lines（人读、评审版）
├── cases.json                # 统一 schema 评测用例（复用 golden/retell 真句，补预期行为字段）
├── run_tutor_judge.py        # 驱动器：读 cases → 跑被测对话 → 存 trace → 判分 → 出报告
├── judge.py                  # 三层 judge：程序断言 / LLM-judge / 红线硬判
├── report.md                 # （生成本身不入库，reports/ 存版本化结果）
└── README.md                 # 版本冻结、运行命令、回归门槛说明
```

**三层并联分工**（源自你的《Skill评估体系》三类提示词）：

| 层 | 判什么 | 实现 | 何时用 |
|---|---|---|---|
| L1 程序断言 | 偏误定位对不对（span/type/correction）、漏判/误报、复述验证有无执行 | 确定性代码 | 字段完全确定处 |
| L2 LLM-judge | 讲解完整度、话术自然度、语言分层是否守约、介入时机合理性 | 独立 LLM 按 rubric 打分 | 开放质量问题 |
| L3 红线硬判 | 教错 / 误报干净句 / 漏复述验证 / 流利时过度打断 / 归因污染图谱 | 程序 + LLM 复核 | 单独一票否决，不进平均分 |

## 四、HSK 领域 Rubric（草稿 for rubric.md）

**评分维度（6 条，各 1–5 分）**，源自你已定的教学法原则：

1. `偏误定位准确` — 是否瞄准真错点（对齐 `error_span`/`error_type`/`correction`），不误报、不教错
2. `讲解四段完整` — 为什么错 → 正确说法 → 对比 → 验证 是否齐全
3. `复述验证严格` — 是否让学习者复述、连续 2 次不过是否降难度、是否拒绝"假懂"
4. `介入时机合理` — 三档是否匹配难度/求助，是否过度打断
5. `语言分层守约` — 英文脚手架 + 中文内容载体（0.21 原则）
6. `归因谨慎` — L1 迁移假设是否讲得谨慎、不污染图谱（0.22 原则）

**Red lines（5 条，触发任一 → 该 case pass=false，直接阻断）**：
- R1 教错了（correction 本身错误，即实际 correction ≠ 黄金 correction）
- R2 误报干净句（clean 句被当偏误纠）
- R3 漏了复述验证（讲解完没让学习者验证）
- R4 流利时过度打断（高置信流利句仍介入）
- R5 归因污染图谱（把假设当事实写进图谱）

## 五、Case schema：复用现有黄金集 + 补字段（不改数据本体）

首版从 `golden_v1_4.json` + `retell_golden.json` 抽取真句，**只新增评测视图，不改写原数据集**。统一 schema：

```json
{
  "id": "TQ-001",
  "source": "golden_v1_4|retell_golden",
  "source_id": "HSK1-ERR-002",
  "case_type": "error_recognize|explain|retell|intervention|clean_guard",
  "input": "我想买苹果很多。",
  "context": null,
  "expected_behavior": {
    "detect": { "span": "苹果很多", "type": "语法", "correction": "很多苹果" },
    "must_explain": true,
    "must_verify": true
  },
  "redlines": ["R1", "R2", "R4"],
  "gold_judge_hint": null,
  "metadata": { "learner_level": 1, "native_lang": "英语" }
}
```

- `case_type` 决定触发哪一层 judge（`clean_guard` 触发 R2 红线，`retell` 触发 L2 验证严格度）。
- 判分口径对齐你的知识库：事实类（定位、类型、改法）→ L1 程序断言对黄金字段；开放类（讲解、话术、语言分层）→ L2；红线 → L3 硬判。
- `gold_judge_hint` 用于人工样本来校准 L2，首版对关键 case 填 human gold。

## 六、运行与回归门槛

```
python -m datasets.eval.tutor_quality.run_tutor_judge
# 无 API Key：--mock（只跑 L1 程序断言 + 红线，L2 跳过后标记，学现有 eval --mock 约定）
```

**回归门槛**（对齐你定的"红线一律 fail"）：
- 任一 **red line 触发 → 整体 fail**（红线不参与平均分，单独列出）
- 维度分：每 case 输出 6 维分 + 汇总通过率
- `pass^k-style`：累计 pass 率 < 阈值（首版 90%，可调）→ 门禁失败，写入测试套件
- 结果落 `reports/eval_tutor_quality_YYYYMMDD.md`，含主机/模型/数据版本/日期（学你知识库"无 Trace 无评测 + 版本冻结"铁律）

## 七、数据与模型版本冻结

- 每次跑在 README 记录：模型、prompt 版本、case 版本、日期。
- case 文件冻结版本；改 case 需升版并记录，不偷偷改题（对齐《评测数据集构建》"冻结版本避免结果无法比较"）。
- LLM-judge 结果的校准：首版人工核 20 个 case 的 L2 判定，报告 judge 与人工一致率（学 G-Eval/Anthropic 用 human gold set 校准，不只看 judge 自报分）。

## 八、Roadmap（工程分步）

1. 建 `tutor_quality/` 目录 + `rubric.md` + 统一 `cases.json`（从 golden/retell 抽首版 ~20 条，覆盖 error_recognize/explain/retell/clean_guard 四类）
2. 写 `judge.py`：L1 程序断言（对黄金字段）+ L3 红线硬判（先做纯规则 R1/R2，R3/R4/R5 后续接 LLM 复核）
3. 写 `run_tutor_judge.py`：读 case → 调被测对话 → 存 trace → 判分 → 报告
4. L2 LLM-judge 接入 rubric.md，人工 gold 校准 20 条
5. 挂进测试/CI 作为回归门槛
6. badcase 回流：线上失败归因（Badcase归因SOP）→ 新 case 进 regression 子集

## 九、待你确认的开放点

1. **阈值 90%** 是否合适，还是更严格。
2. **首版 case 数量约 20 条** 是否接受（先小范围定标准，按你的《本地评测落地》"先 20 条起步"建议）。
3. **两条合规约束**：①我不把真实学习者数据上传任何外部平台，只用本地脱敏/虚构/既有黄金集数据；②本设计文档 + 后续代码先交你审，不直接动实现（符合项目"先设计再执行"约束）。
