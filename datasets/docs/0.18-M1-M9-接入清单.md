**现状（代码实测）**
- `engine/memory/learner_memory.py`（`LearnerMemory`，落盘 `data/memory_<learner_id>.json`，append/touch/get_history/to_llm_history/get_summary）**已实现且 12 条测试全绿**。
- 但 `engine/serve.py::_do_api_dialog` 直接透传前端 `payload.history`；`planner/loop.py::run` 拿到 `history` 后仅拼进 messages，**不读盘、不落盘**。→ 自由对话当前**无状态**。

**设计依据（agent-design M5「与 planner 的衔接」）**
> `run(user_input, history, learner_id)` 的 history 来自长期文件按窗口截取；会话结束把新对话写回长期文件。

**要改**
| 文件 | 动作 |
|---|---|
| `engine/serve.py` | `_do_api_dialog` 改为：从 `LearnerMemory(learner_id)` 读 `to_llm_history(session_id)` 作为注入历史（替代/合并前端透传）；本轮 user 输入 + assistant 回复在结束后 `append` 回记忆 |
| `planner/loop.py` | 明确 `history` 来源语义（现为透传占位，改为"由上层从记忆注入"）；`learner_id` 已作参数保留 |

**已定决策（2026-09-01 · 经 OpenMAIC + 主流框架一手调研确认）**

1. **session 生命周期 = 复用 + 按任务可切新。**
   前端 `/api/dialog` 传 `conversation_id` + `learner_id`；同一次纠错对话复用同一 `conversation_id`，切换知识点/课程/隔天开新 id；长期画像永远按 `learner_id` 跨 session 检索。
   - 依据：OpenMAIC `runtimeSessionId(stageId :generation: learnerKey :chatSessionId)` 设计表明"同一 session.id 长期复用 + 服务端按学习者/课堂合并状态"，前端是向已有 sessionId 发消息而非每次新建（`lib/utils/chat-storage-core.ts`）；LangGraph/LangMem、Letta、Zep 一致——同 thread 复用、任务切换开新、user 级长期检索。
2. **记忆文件结构 = 嵌套 `profile` + `sessions[]`。**
   保留现有 `data/memory_<learner>.json` 的 sessions 嵌套（含 id/title/status/message_ids/messages），把 `profile` 提为**顶层显式块**；常错点事实带 `confidence / source_session_id / updated_at`（fetched 自偏误图谱确认项，即 M8 `build_profile_summary` 的落点）。
   - 依据：OpenMAIC 双记录（`chat_message` + `chat_session_state` + `messageIds` 快照，`MAX_MESSAGES_PER_SESSION=200`）；Letta `core_memory.blocks` / `archival_memory` / `conversations[]` 三层分离；LangMem/Mem0 画像 facts 用 upsert 且带 confidence/time，episodic(历史) 用 append。**不采用扁平 `profile+history[]`**（历史无法按会话组织/检索）。

**验收**
- 连续两轮"那区别呢"能沿用上文（上一轮主题仍在上下文）。
- `data/memory_<learner>.json` 落盘；换会话/重启后能读到历史。
- 写入中断/异常不损旧文件（原子写，已有测试佐证）。

## 接入项②  M7 RAG → 补 `retrieve_corpus` 技能并注册  ✅ 已完成（2026-09-01）

**落地记录**
- `skills/retrieve_corpus.py`（第 9 个注册技能）：`run({query, top_k, kp_only, level})` → top-k 片段 + 来源（`chunk_id/source/kp_id/knowledge_point/level/text/note/score/in_graph`，来源齐备供引用防编造）。top_k 默认 5、clamp 1-10；level 归一（'HSK3'/'3'/3 → 3，复用 `normalize_level_int`）；未命中返回 `_error` 如实报、不编造。

## 接入项③  M8 记忆×图谱打通 → 画像/惯犯进 planner  ✅ 已完成（2026-09-01）

**闭环核对结论（先核对后动手）**
- 图谱"疑似侧"**本就在对话链**：`IdentifyErrorsSkill._write_graph` 已按 router.process 同语义写图谱（确认偏误 upsert 节点 / uncertain 入 pending / 同句≥2 KP 建混淆边，event_key 幂等）。
- 真缺的是**账本侧**：ledger 事件（惯犯数据源）与确认侧（concept_confirmed）在对话路径从不发生；`Writeback` 仅 generate/practice 路径构造。

**落地记录**
- `engine/serve.py`：
  - `_get_writeback(learner_id)`：按 learner 缓存 `Writeback(graph, learner_id, root=memory_root)`（ledger 落 `data/ledger_<learner>.json`）。
  - `_writeback_ledger_events(wb, trace, user_input)`：**从 planner trace 编排账本事件**——identify 命中 → `ledger.record("observation_error")`（惯犯判定数据源）；verify_retell verdict=pass → `wb.on_confirmed(kp)`（确认侧）。图谱写仍留技能内，此处只补事件账本，不重写图谱（避免 event_key 双写）。
  - **跨轮确认兜底**（自 review 补）：真实流程是"轮1 识别讲解 → 轮2 复述 pass"，同轮 trace 无 identify。`_unconfirmed_recent_kps(ledger)` 从账本推导"最近观察过且其后无确认"的 KP（列表下标判定顺序，倒序最多 3 个）作确认对象。
  - 画像注入：`build_profile_summary(graph, ledger)` 每轮注入 planner system；`build_profile_facts` 写回 `mem.profile.common_errors`（图谱×账本×记忆三线汇合）。写入失败仅记 degraded 通知，不阻塞对话。
- `planner/loop.py`：`run(..., profile_summary=None)` 接收摘要拼进 system（【学习者画像】段）；GLOBAL_RULES 加规则 7（讲相关知识点主动点出高频偏误；开场/收尾主动复习提醒，可调 get_review_queue）。
- `engine/memory/summarize.py`：新增 `build_profile_facts()`（结构化 facts，与 build_profile_summary 同源）。
- 测试：`tests/test_dialog_profile.py` 4 用例（惯犯闭环+画像注入+facts 汇合 / verify pass-fail 确认控制 / 跨轮确认 / 冷启动无画像不注入）。全量 182 → 186 全绿。

**自 review 修复（2026-09-01，3 处 ledger 语义 bug，直接威胁惯犯判定准确性）**
- `error_ledger.repeated_count` 原数**所有**事件：错 2 次 + 确认 1 次 = 3 → 被误判惯犯（阈值恰为 3）。修复：只数 observation_error/repeated_error（撞错事件），确认/复习不计入（宁漏勿错）。

- `build_profile_facts.latest_evidence` 原取最近任意事件：确认一次后错误原句被"复述验证通过"覆盖。修复：只取观察类事件证据。
- 补回归：`tests/test_m8.py` +3 用例（确认不推高计数 / 二次确认不误标 / latest_evidence 保住错误原句）。全量 **189 全绿**。

### 接入项④a 落地记录（2026-09-01）

- `skills/base.py` 新增 `Skill.validate_params()`：零依赖轻量校验器（JSON Schema 子集：type/required/enum/properties）。**宽松纠正取向**——LLM 常见错型自动纠正（'3'→3、'true'→True、数字→字符串、enum 大小写不敏感匹配），不可安全纠正的（缺必填/空值、bool 硬当 int、array/object 形态错、enum 越界）返回结构化错误；未声明字段放行（planner 常带上下文字段，宁宽勿严）；注意 Python bool 是 int 子类须先排除。array 不自动包装（掩盖形态错误更危险）。
- `planner/loop.py::_dispatch_action`：调用前校验，失败 → 技能不执行 + `skill_error_reply` 喂回 LLM 下一轮自纠（**不打 fallback**——对标 Anthropic is_error tool_result 模式与业界"多数前沿模型二轮可自纠"实测）。MAX_STEPS=6 兜底防死循环。
- `skills/generate_unit.py` 补 output_schema（此前唯一缺失）。
- **前端消费方修复（review 发现的既有 bug，被校验拦截放大）**：`renderTrace`/`cardSummary` 原不区分 `t.ok`——校验失败/技能异常条目会渲染成误导性"这句话没有发现高置信偏误"绿卡、并写进多轮学习记录摘要（污染记忆）。两处加 `t.ok===false` 跳过（失败调用无学习成果，宁漏勿错）。
- **行为变化（显式锁定）**：verify_retell 空 explanation 从技能内降级 partial（verdict 正常返回）改为校验器拦截喂回自纠；lookup_knowledge_point 保持无硬 required（kp_id/keyword 二选一语义在技能内检查）；空数组（如 key_points=[]）仍走技能内降级（区分"没传"与"传了空的"）。
