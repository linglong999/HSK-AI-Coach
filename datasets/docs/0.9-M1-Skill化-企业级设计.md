# 0.9 · M1 Agent Skill 化 — 企业级设计文档

> **对齐**：承接 `0.6-Agent能力基座` 决策块 7.2「Skill 封装三引擎（能力单元化）」——把三核心引擎扩展为五内核技能，落地成可被 LLM 调用、可复用、可测试、可编排的能力单元。
> **定位**：企业内部级 Skill（理论认知 / 范式参照 / 工程实现 / 实证迭代 / 生态维护 **五层全覆盖**）。部分层（理论/范式/生态）**不进入 SKILL.md 文件本身**，但作为设计的可讲性与可维护性支撑。
> **范围**：本 M1 只做 **薄壳适配 + 注册表 + 触发评测**。引擎（recognizer/explainer/verifier/graph/llm）**一律不动**，原有 32 个无 Key 测试保持 PASS。零第三方依赖（仅标准库）。
> **状态**：设计待你拍板，未写代码。

## 0. 一句话定位

> **M1 是把"强在对的引擎"包装成"好调用的技能"，并用评测证明调用可靠。**

引擎已存在且已验证（recognizer F1 0.97、verifier 判定一致性 88.2%、图谱 18/18 PASS）。M1 不重写引擎，只做：
1. 给每个引擎套一层**程序化双形态** Skill 壳（`run()` 执行 + `to_manifest()` 描述）。
2. 建 `SkillRegistry`（注册 / 查询 / 两级清单渲染）。
3. 建**触发评测集**（should-trigger / should-not-trigger），评测驱动、失败优先。

| 层 | 定义 | 在本项目 M1 的具体落点 | 是否进 SKILL.md |
|---|------|----------------------|:---:|

## 3. 五内核 Skill 的输入/输出契约（run() 入参映射设计）

> 设计原则（对应你知识库）：**参数匹配用户意图层级，转换责任交给 Skill 内部代码，不让 LLM 编造**；`user_level`/`native_lang` 由 **planner/框架注入**，Skill 不自己获取上下文。

### 3.1 `identify_errors` — 包 `Recognizer.recognize()`
| 字段 | 类型 | 必选 | 说明 |
|---|---|---|---|
| `text` | str | ✅ | 用户给的整句 |
| `level` | str | ⭕ | 学习者等级，默认 HSK3（注入，非技能自取）|
| 输出 | dict | — | 对齐 JSON 接缝契约 v1：`errors[]`/`uncertain[]`/`degraded[]` |

### 3.2 `explain_error` — 包 `Explainer.explain()`
| 字段 | 类型 | 必选 | 说明 |
|---|---|---|---|
| `error` | dict | ✅ | 识别出的一个偏误（fragment/correction/type/confidence/knowledge_point_id）|
| `sentence` | str | ✅ | 原句 |
| `user_level` / `native_lang` | str | ⭕ | 注入 |
| 输出 | dict | — | 讲解 + key_points（正向知识）+ 修正解释 |

### 3.3 `verify_retell` — 包 `Verifier.verify()`（router 已透传 commit_graph=True）
| 字段 | 类型 | 必选 | 说明 |
|---|---|---|---|
| `explanation` | str | ✅ | 讲解内容 |
| `key_points` | list | ✅ | 要点（覆盖集）|
| `restatement` | str | ✅ | 学习者复述 |
| `event_key` | str | ⭕ | 幂等键（写回图谱）|
| 输出 | dict | — | 逐点判定 + pass/partial/fail 聚合 + 写回图谱 |

### 3.4 `lookup_knowledge_point` — 包 `knowledge_points_v1_4.json`
| 字段 | 类型 | 必选 | 说明 |
|---|---|---|---|
| `kp_id` 或 `keyword` | str | ✅ | 知识点 id 或名称关键词（高层级意图，查询逻辑在 skill 内）|
| 输出 | dict | — | 匹配的 kp（knowledge_point/level/error_types/note）|

### 3.5 `get_review_queue` — 包 `ErrorGraph.get_review_queue()`（⭐ 突出）
| 字段 | 类型 | 必选 | 说明 |
|---|---|---|---|
| `learner_id` | str | ⭕ | 默认 default（注入，非技能自取）|
| 输出 | dict | — | 按 priority 降序的待复习知识点列表 + 关联偏误 |

## 4. 工程实现设计（层③）

### 4.1 目录结构（与 engine 平级，零第三方依赖）
```
skills/
  base.py                 # Skill 抽象基类
  registry.py             # SkillRegistry：register / get / list_all
  identify_errors.py
  explain_error.py
  verify_retell.py
  lookup_knowledge_point.py
  get_review_queue.py
  # 预留（登记类型位，后置）：generate_quiz / pronunciation_assessment / roleplay_conversation
eval/
  skill_trigger_eval.json  # 触发评测集（should/should-not）
  run_skill_trigger_eval.py
```

### 4.2 `base.py` — Skill 抽象基类（程序化双形态）
```python
class Skill:
    metadata = {  # 供 LLM 发现：对应官方 frontmatter 的 name/description
        "name": ...,          # 简洁 slug，≤64 字符
        "version": ...,       # 语义版本，升级引擎不改 name
        "summary": ...,       # 一句话作用
        "triggers": ...,      # 何时该用（正例+反例）
        "guardrails": ...,    # 何时不要用，防 planner 误选
        "input": ...,         # 入参说明 + 示例
        "output": ...,        # 返回结构说明
    }
    input_schema = ...        # 供 planner 校验与生成调用
    output_schema = ...
    def run(self, context) -> dict: ...          # 调引擎（薄适配）
    def to_manifest(self) -> dict: ...           # 渲染完整四段式详情（对应 SKILL.md 层）
```

### 4.3 `registry.py` — SkillRegistry（两级渲染）
- 内部：`name -> Skill 实例` 字典。
- `register(skill)`：重名抛异常；`get(name)`；`list_all()`。
- **两级渲染**（对应"渐进式披露"：先紧凑清单省 token，选中看详情）：
  - 第一级 `list_all()`：每技能一行（`name · summary · triggers` 一句）。
  - 第二级 `get(name).to_manifest()`：完整 summary/triggers/input/out/guardrails（仅在决定调用前展开）。
- **对齐官方规范**：`list_all()` = description 触发层；`to_manifest()` = SKILL.md 正文层；`run()` = scripts 执行层。三级渐进披露。

### 4.4 `identify_errors.py` — 首个规范 Skill（镜像样板）
原则：**不改 `Recognizer` 任何代码**。技能只做：入参映射（text/level）→ 调 `recognize()` → 出参封装（契约 v1 对齐）。作为其余 4 技能的统一样板（字段/描述风格/异常处理一致）。

## 5. 实证迭代设计（层④）— 评测驱动、失败优先

> 对齐你知识库「Skill评估体系四维」+「评测驱动、失败优先六步法」+ 官方 skill-creator「should-trigger/should-not-trigger」。

### 5.1 第一步：建触发评测集（评测驱动先行，M1 就做）

> **设计原则（本轮你纠正后确立）**：评测集必须载**真实歧义**，不是 toy 案例。核心是测"**语义相近但触发不同技能**"的判断力——LLM 是 Skill 的调用者，它最常错的就是"句子像又不像该调某个技能"的灰区。

`eval/skill_trigger_eval.json` 按**触发层级**组织，分四组：

```json
{
  "layer": "skill_trigger",
  "groups": {
    "A_no_trigger": {
      "desc": "不该触发任何技能（精确率——防误触发）",
      "cases": [
        {"query": "帮我用中文点评一下这段文章", "expect": [], "why": "点评≠识别偏误"},
        {"query": "今天北京天气怎么样", "expect": [], "why": "闲聊"},
        {"query": "把这段话翻译成英文", "expect": [], "why": "翻译≠任何内核技能"}
      ]
    },
    "B_direct_trigger": {
      "desc": "单一技能精确触发（召回率——该调的漏调）",
      "cases": [
        {"query": "我想买苹果很多。", "expect": ["identify_errors"], "why": "给了整句求找错"},
        {"query": "'把'字句是什么？", "expect": ["lookup_knowledge_point"], "why": "求知识点定义"},
        {"query": "我最近该复习什么？", "expect": ["get_review_queue"], "why": "求个性化复习队列"}
      ]
    },
    "C_full_loop": {
      "desc": "一句话触发完整纠错闭环（识别→讲解→验证）——连续技能链",
      "cases": [
        {"query": "这句话有语病吗？帮我改一下。", "expect": ["identify_errors", "explain_error"], "why": "找错+改错连问，但默认不进入复述验证"},
        {"query": "我觉得这句子不对，你讲讲为什么。", "expect": ["identify_errors", "explain_error"], "why": "先认错，后解释——强制先识别再讲解"}
      ]
    },
    "D_ambiguity": {
      "desc": "核心歧义组——语义相近但触发不同技能（本项目最难、最该测的）",
      "cases": [
        {"query": "这句话有错吗？", "expect": ["identify_errors"], "why": "求判断→只识别，不讲解"},
        {"query": "这句话为什么不对？", "expect": ["identify_errors", "explain_error"], "why": "求解释→识别后必须讲解，比上一句多一步"},
        {"query": "我写的对还是不对？", "expect": ["identify_errors"], "why": "求对错判定→先识别；若对则无需讲解"},
        {"query": "老师，这样用对吗？", "expect": ["identify_errors"], "why": "问用法对错→识别；无问 why 不必讲解"}
      ],
      "note": "判据：'有错吗/对吗'=仅识别；'为什么不对/讲讲'=识别后须讲解。动词与疑问词决定技能链深度——这正是 LLM 最易错、触发评测必须卡的灰区。"
    }
  }
}
```

**为什么这样建（对齐你"评测驱动、失败优先"）**：
- **A 组**（不该触发）守**精确率**：题面带"点评/翻译/天气"，但都不是偏误教学——防 LLM 对任何句子都想调某个技能。
- **B 组**（直达触发）守**召回率**：确保该召回技能时必召回。
- **C 组**（闭环链）守**技能链正确性**：纠错场景默认带出 识别→讲解，但**默认不进入复述验证**（复述需要学习者主动输出，不应自动触发）。
- **D 组**（核心歧义）是**主角**：同一主题（一句话对错）通过**疑问词层级**区分技能链深度——"有错吗/对吗"→仅识别；"为什么不对/讲讲"→识别后讲解。这直接映射你说的"都该触发但触发不同技能"，是评测真正在捍卫的价值。

**数量建议**：每组 4-8 条，总 20-30 条（对齐你知识库"50 条测试输入统计调用命中率"的量级，但先小后扩，M1 先 20-30 条+后续随真实失败补充）。

**指标**：
- **触发精确率** = A 组不误报 + 各 case 命中集 ⊆ expect（防多调）
- **触发召回率** = B/C/D 组 对应技能 ∈ 命中集（防漏调）
- **技能链正确性** = C/D 组的"识别是否带出讲解"严格命中断言

**无 LLM Key 时**：先跑**规则级触发自测**（用关键词/疑问词规则层近似判定，断言命中的技能），产出 A/B/C/D 分组指标。LLM 层触发评测留待 M6 有 Key 时叠加。

### 5.2 与 M6 的关系
- M1 建 `run_skill_trigger_eval.py` 只测**触发**（该调技能吗）。
- M6 自由对话评测再叠加**执行质量**（调对后结果对不对）+ LLM-judge。
- M1 是 M6 的前置地基，非替代。

## 7. 生态 / 面试叙事（层⑤ + 可讲性）

**可讲的设计决策（面试/评审证据）**：
- "我把强在对的引擎包装成好调用的技能，**不重写引擎**——因为引擎已用评测验证过（F1 0.97），M1 的价值在复用与可编排，不在重造。"
- "技能用**程序化双形态**：能 run() 执行，又能 to_manifest() 给 LLM 看描述——同时满足工程执行与渐进式披露。"
- "我用**评测驱动**：先建 should/should-not 触发集，再写技能，评测是约束、技能是实现。"
- "**get_review_queue 是差异化**：个性化记忆（偏误图谱→复习队列）是 OpenMAIC 没有的，单独立壳突出。"

**生态维护**：metadata.version 语义版本化；技能名稳定（升级不改 name，只 bump version）；注册表 = 单一发现点；发布前跑 32 测试 + 触发评测门禁。
